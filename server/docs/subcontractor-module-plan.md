## ส่วน 1 — เคส 2.1 เงินล่วงหน้า (Advance Payment)

### บัญชีใหม่ที่ต้องมี
**ต้องมีบัญชีใหม่ — ใช้บัญชีเดิมไม่ได้** เสนอ `1160 เงินจ่ายล่วงหน้าผู้รับเหมาช่วง` (สินทรัพย์ ประเภท
เดียวกับ `1150`/`1200` — เป็นเงินที่จ่ายออกไปแล้วแต่ยังไม่ตัดเป็นต้นทุนจริง จนกว่าจะมีงวดงานมาหักคืน)

### ผัง Dr/Cr ตอนจ่ายเงินล่วงหน้า
ตัวอย่างจริงตามที่ให้มา: สัญญา 1,000,000, จ่ายล่วงหน้า 15% = 150,000

```
Dr 1160 เงินจ่ายล่วงหน้าผู้รับเหมาช่วง        150,000
   Cr 2120 ภาษีหัก ณ ที่จ่ายค้างนำส่ง                  4,500   (150,000 × 3% ⚠️ ดูหัวข้อ "มี WHT ไหม" ด้านล่าง)
   Cr 1100 เงินสด/ธนาคาร                             145,500
```

### มี VAT ไหม — ⚠️ ไม่แน่ใจ ต้องยืนยัน
ภาษีมูลค่าเพิ่มสำหรับบริการ (รวมงานรับเหมาก่อสร้าง) เกิดขึ้น ณ วันที่ **เร็วที่สุด** ระหว่างวันที่ชำระเงิน
กับวันที่ออกใบกำกับภาษี — เงินล่วงหน้าคือการชำระเงินจริง จึงมีโอกาสเข้าเงื่อนไขต้องมี VAT ทันที **ถ้า**
ผู้รับเหมาออกใบกำกับภาษีให้ตอนรับเงินล่วงหน้า แต่ถ้าผู้รับเหมาเก็บใบกำกับภาษีไว้ออกตอนงวดงานจริงแทน
(บางรายทำแบบนี้) ก็ไม่มี VAT ตอนนี้ — **ขึ้นอยู่กับพฤติกรรมผู้รับเหมาแต่ละรายจริง ไม่ใช่กฎตายตัว** ระบบ
ควรออกแบบให้ยืดหยุ่น (มี toggle `has_tax_invoice` ต่อรายการเหมือนโมดูล 1.3/1.4) ไม่ใช่ hardcode ว่ามี/ไม่มี

### มี WHT ไหม — ⚠️ ไม่แน่ใจ ต้องยืนยัน (เสนอ default = มี)
เงินล่วงหน้าคือ "การจ่ายเงินได้" จริงตามความหมายมาตรา 3 เตรส — หลักการทั่วไปคือ **ต้องหัก ณ ที่จ่ายทันที
ที่มีการจ่ายเงิน ไม่ว่าจะเป็นเงินล่วงหน้าหรือเงินงวดปกติ** เสนอให้ default เป็น **มี WHT** ตามตัวอย่างที่คำนวณ
ไว้ด้านบน (4,500 บาท) — แต่ยังต้องยืนยันกับฝ่ายบัญชีว่าตรงกับแนวปฏิบัติจริงของบริษัท เพราะบางบริษัทเลือก
หัก WHT ทีเดียวตอนเคลียร์งวดสุดท้ายแทน (ไม่ใช่แนวทางที่ถูกต้องตามกฎหมายเป๊ะ แต่พบเป็นแนวปฏิบัติจริงได้)

## ส่วน 2 — การหักคืนเงินล่วงหน้าใน 2.2 (จุดซับซ้อนที่สุด)

ตัวอย่างจริงตามที่ให้มา:
```
สัญญา                 1,000,000
จ่ายล่วงหน้า 15%          150,000  (จ่ายไปแล้วในส่วน 1)
งวดนี้เบิก               200,000
หักคืนเงินล่วงหน้า 15%      30,000  (= 200,000 × 15%)
กัน retention 5%           10,000  (= 200,000 × 5%)
WHT 3%
```

### ⚠️ WHT คำนวณจากฐานไหน — จุดที่ไม่แน่ใจที่สุดในแผนทั้งหมด

มี 2 ทางที่เป็นไปได้ ทั้งคู่มีเหตุผลรองรับ ต้องให้ฝ่ายบัญชีชี้ขาด:

**ทางที่ 1 (เสนอเป็น default)**: ฐานคือ **มูลค่างวดงานเต็มจำนวนที่รับรอง (200,000) — ไม่ลดฐานด้วย
retention หรือเงินล่วงหน้าที่หักคืน** → WHT = 200,000 × 3% = **6,000**
เหตุผลสนับสนุน: มูลค่างานที่ "เกิดขึ้นจริง/ถูกรับรองแล้ว" ในงวดนี้คือ 200,000 เต็มจำนวน — retention
เป็นแค่การเลื่อนจ่ายเงินสด (งานยังเป็นของผู้รับเหมา ยังไม่ได้ลดมูลค่างานลง) และเงินล่วงหน้าที่หักคืนก็เป็น
แค่การหักกลบหนี้เดิมที่เคยจ่ายไปแล้ว (ไม่ใช่ลดมูลค่างานงวดนี้) แนวทางนี้ตรงกับที่ใบกำกับภาษี VAT มักออก
บนมูลค่างวดเต็มจำนวนเสมอ (retention/เงินล่วงหน้าไม่ใช่ตัวลดฐาน VAT) — ใช้ตรรกะเดียวกันกับ WHT

**ทางที่ 2**: ฐานคือ **ยอดที่จ่ายเงินสดจริงเท่านั้น** (200,000 - 30,000 หักคืนล่วงหน้า - 10,000
retention = 160,000) → WHT = 160,000 × 3% = 4,800
เหตุผลสนับสนุน: หน้าที่หัก ณ ที่จ่ายผูกกับ "การจ่ายเงิน" จริง — ส่วนที่ยังไม่จ่าย (retention) หรือหักกลบไป
แล้ว (เงินล่วงหน้าที่เคยหัก WHT ไปแล้วตอนจ่ายจริง) ไม่ควรถูกนับซ้ำเป็นฐานคำนวณอีกรอบ

**ผลต่างระหว่าง 2 ทาง = 1,200 บาทต่องวด** (6,000 vs 4,800) — ไม่ใช่เรื่องเล็ก ต้องเลือกให้ถูกก่อนเขียนโค้ด
จริง เอกสารนี้จะ**ยึดทางที่ 1 เป็น default ในตัวอย่างคำนวณด้านล่างทั้งหมด** จนกว่าฝ่ายบัญชีจะแก้ไข

### retention คำนวณจากฐานไหน
**ไม่กำกวมเท่า WHT** — ตามธรรมเนียมทั่วไปและตรงกับที่ผู้ใช้ให้ตัวเลขมา: retention คำนวณจาก **มูลค่างวด
งานเต็มจำนวน (200,000) เสมอ** ไม่ใช่ยอดหลังหักอะไรทั้งสิ้น = 200,000 × 5% = 10,000 ตรงกับตัวอย่างที่ให้มา
พอดี — เหตุผล: retention คือ "ประกันผลงาน" ของมูลค่างานที่ส่งมอบ ไม่เกี่ยวกับกลไกการจ่ายเงินเลย

### ลำดับการหัก (มีผลต่อยอดสุทธิ)
ยืนยันว่า**ลำดับไม่กระทบยอดสุทธิสุดท้าย** เพราะทุกรายการ (หักคืนเงินล่วงหน้า, retention, WHT) คำนวณจาก
ฐาน "มูลค่างวดเต็มจำนวน 200,000" อิสระต่อกันทั้งหมด ไม่มีรายการไหนคำนวณจากผลลัพธ์ของอีกรายการ (ต่างจาก
เช่น ถ้า WHT ต้องคำนวณจากยอดหลังหัก retention ก่อน แบบนั้นลำดับจะมีผลจริง) — **ข้อนี้เป็นเหตุผลเพิ่มเติมที่
สนับสนุนทางที่ 1 ของคำถาม WHT ด้านบน**: ถ้าเลือกทางที่ 1 (ฐาน WHT = มูลค่างวดเต็ม) การคำนวณทั้งหมดจะ
ทำแบบขนานกันได้ ไม่ต้องกังวลเรื่องลำดับเลย ซึ่งเขียนโค้ดและตรวจสอบง่ายกว่าทางที่ 2 มาก (ทางที่ 2 ต้อง
คำนวณ retention/advance recovery ก่อน แล้วค่อยคำนวณ WHT จากผลลัพธ์ ทำให้ลำดับมีผลจริง)

### ผู้รับเหมาได้เงินจริงเท่าไหร่ (ใช้ทางที่ 1 เป็นฐานคำนวณ)
```
มูลค่างวดงาน                    200,000
หัก เงินล่วงหน้าที่หักคืน          (30,000)
หัก เงินประกันผลงาน (retention)   (10,000)
หัก ภาษีหัก ณ ที่จ่าย (WHT 3%)      (6,000)
                              ─────────
สุทธิที่จ่ายจริง                  154,000
```

### ผัง Dr/Cr ตอน approve งวดงาน
```
Dr 5200 ต้นทุนผู้รับเหมาช่วง                200,000   (มูลค่างวดเต็มจำนวน)
   Cr 1160 เงินจ่ายล่วงหน้าผู้รับเหมาช่วง             30,000   (หักคืนเงินล่วงหน้า)
   Cr 2140 เงินประกันผลงานค้างจ่าย                10,000   (กัน retention)
   Cr 2120 ภาษีหัก ณ ที่จ่ายค้างนำส่ง                 6,000   (WHT — ทางที่ 1 ⚠️)
   Cr 2130 เจ้าหนี้ผู้รับเหมาช่วง                  154,000   (สุทธิที่ต้องจ่ายจริง)
```
ตรวจสมดุล: Dr 200,000 = Cr (30,000+10,000+6,000+154,000) = 200,000 ✓

**ถ้ามี VAT** (ผู้รับเหมาออกใบกำกับภาษีเต็มรูปงวดนี้ — ตัวอย่างผู้ใช้ไม่ได้ระบุ VAT มาด้วย จึงไม่รวมใน
ตัวอย่างหลัก): เพิ่ม `Dr 1170 ภาษีซื้อ = 200,000 × 7% = 14,000` และ `Cr 2130` เพิ่มขึ้นเท่ากับ VAT (ผู้
รับเหมาได้ VAT คืนเต็มจำนวน ไม่ถูกหักด้วย retention/advance recovery — ใช้ gate `has_tax_invoice`
เดียวกับโมดูล 1.3/1.4)

### ผัง Dr/Cr ตอนจ่ายเงินจริง

## ส่วน 3 — ยอดคงเหลือที่ต้องติดตาม

**ยังไม่มีที่เก็บ** — `client_subcontract_terms` ไม่เคยถูกสร้างจริง (เคยร่างไว้ในแชทช่วง batch 2 เท่านั้น
ไม่เคยบันทึกลงไฟล์ ไม่มีร่องรอยในโค้ด/migration ใดๆ เลย ตรวจสอบแล้วจากทั้ง repo) — เอกสารนี้ร่างคอลัมน์
ใหม่ทั้งหมดในส่วน 4 ด้านล่าง

**หลักการที่ต้องยึดตาม CLAUDE.md**: ยอดคงเหลือทั้ง 3 ตัวนี้ **ต้องเป็นค่าที่คำนวณสด (SUM) ตอนอ่าน ไม่ใช่
คอลัมน์ตัวเลขที่ update สะสมทับ** (แพทเทิร์นเดียวกับ `CLIENT_PETTY_CASH_FUND_BALANCE_SUBQUERY` ที่ใช้อยู่
แล้วในโมดูล 1.1) — ป้องกัน lost-update ตอน concurrent approve เหมือนที่เคยแก้บั๊กจริงมาแล้วในกองทุน
เงินสดย่อย

1. **เงินล่วงหน้าคงค้าง** = `SUM(gross_amount ที่ billing_type='advance' และ approved)` −
   `SUM(advance_recovery_amount ที่ billing_type='progress' และ approved)` ต่อสัญญา
2. **Retention สะสมรายสัญญา** = `SUM(retention_amount ที่ billing_type='progress' และ approved)` −
   `SUM(gross_amount ที่ billing_type='retention_release' และ approved)` ต่อสัญญา
3. **ยอดเบิกสะสมเทียบมูลค่าสัญญา** (กันเบิกเกิน) = `SUM(gross_amount ที่ billing_type='progress' และ
   approved)` ต้องไม่เกิน `contract_value` — เช็คตอน submit/approve คล้ายที่ PR เช็ค budget ceiling
   (เทียบฝั่ง SQL ด้วย `::numeric` เสมอ ไม่ใช้ JS Number ตัดสินใจ ตามกฎ CLAUDE.md ข้อ 3)

## ส่วน 6 — ข้อกำหนดเพิ่มเติมสำหรับ `client_subcontract_billings` (ตามที่สั่งเพิ่ม)

### 6.1 กันเบิกเกินสัญญา / กันหักคืนเกินยอดล่วงหน้า / กันคืน retention เกิน

**ทำเป็น CHECK constraint ธรรมดาไม่ได้เลยสักข้อ** — CHECK ผูกกับแถวเดียวเท่านั้น (per-row) แต่ทั้ง 3 กรณี
นี้ต้องเทียบกับ `SUM(...)` ข้ามหลายแถว จึง**ต้องบังคับในโค้ด application ภายใน transaction เท่านั้น**
(เหมือนที่ PR เช็ค `qty_remaining` และกองทุนเงินสดย่อยเช็ค balance) — ลำดับการล็อกต้องคงที่ตาม CLAUDE.md
ข้อ 6: ล็อก `client_subcontract_terms` (header/สัญญา) ก่อนเสมอ แล้วค่อยล็อกแถว
`client_subcontract_billings` ที่เกี่ยวข้อง (ถ้ามี) — และต้องแยก statement ล็อกกับ statement คำนวณ SUM
ออกจากกันตามกฎข้อ 7 (ห้ามรวม `FOR UPDATE` กับ correlated subquery ไว้ query เดียวกัน)

| กรณี | เช็คตอนไหน | สูตร |
|---|---|---|
| เบิกเกินสัญญา | submit หรือ approve แถว `progress` (เลือกจุดเดียวให้คงที่ ⚠️ แนะนำ approve เพราะ draft/submitted ยังแก้ไขได้อยู่ ไม่ควร lock ค่าเกินจำเป็น) | `SUM(gross_amount) ของ progress ที่ approved ทั้งหมด + gross_amount แถวนี้ ≤ contract_value` |
| หักคืนล่วงหน้าเกิน | approve แถว `progress` | `advance_recovery_amount แถวนี้ ≤ เงินล่วงหน้าคงค้าง (ส่วน 3 ข้อ 1) ณ เวลานั้น` |
| คืน retention เกิน | approve แถว `retention_release` | ตรวจทีละแถวใน `client_subcontract_retention_release_items`: `SUM(amount) ของงวดนั้น (รวมครั้งก่อนๆ) + amount ครั้งนี้ ≤ retention_amount ของงวด progress นั้น` |

ทุกการเทียบต้องทำฝั่ง SQL ด้วย `::numeric` แล้วคืน boolean กลับมาตัดสินใจ ไม่แปลงเป็น JS Number ตามกฎ
CLAUDE.md ข้อ 3 — เหมือนที่ `has_enough`/`is_sufficient` ทำอยู่แล้วในโมดูล PR/เงินสดย่อย

### 6.2 คืน retention ต้องรู้ว่าคืนของงวดไหน

ตอบแล้วในตาราง `client_subcontract_retention_release_items` ด้านบน — เลือกใช้ **ตารางลูก** (ไม่ใช่คืนรวม
ทั้งสัญญาทีเดียว) เพราะ:
- แต่ละงวดอาจครบกำหนดคืน retention คนละเวลาจริง (ระยะประกันผลงานมักนับจากวันที่ส่งมอบงวดนั้น ไม่ใช่วันเซ็น
  สัญญา)
- ต้องตรวจสอบย้อนหลังได้ว่า "งวดที่ 3 retention คืนไปหรือยัง" แยกจากงวดอื่น — ถ้าคืนรวมทั้งสัญญาทีเดียว
  จะตอบคำถามนี้ไม่ได้เลยถ้าเคยคืนบางส่วนไปก่อนหน้า

### 6.3 CHECK ผูก `billing_type` กับฟิลด์ที่ใช้ได้จริง

```sql
CONSTRAINT client_subcontract_billings_type_fields_check CHECK (
  status = 'draft' OR
  (billing_type = 'advance' AND advance_recovery_amount = 0 AND retention_amount = 0) OR
  (billing_type = 'progress') OR
  (billing_type = 'retention_release' AND advance_recovery_amount = 0 AND retention_amount = 0
    AND wht_amount = 0 AND vat_amount = 0)
)
```
`status = 'draft' OR ...` ไว้ข้างหน้าเสมอ (แพทเทิร์นเดียวกับ `client_payment_vouchers_payee_type_check`)
— ตอนกรอกฟอร์มยังไม่เสร็จ (draft) ต้องยอมให้ค่าไม่ครบ/ไม่สอดคล้องกันชั่วคราวได้ บังคับเข้มจริงจังตั้งแต่
`submitted` เป็นต้นไปเท่านั้น (ชั้น application ต้องปฏิเสธ `/submit` เองด้วยถ้ายังไม่ครบ ไม่พึ่ง DB CHECK
อย่างเดียวเป็นเกราะสุดท้าย)

### 6.4 เคสไหนออก 50 ทวิบ้าง

| billing_type | ออก 50 ทวิ? | เหตุผล |
|---|---|---|
| `advance` | ⚠️ ตามที่ยังไม่confirmed ในส่วน 1 (default = ออก) | เป็นการจ่ายเงินจริงครั้งแรก ถ้ามี WHT ต้องออกใบตามกฎหมาย |
| `progress` | **ออกแน่นอน** (ไม่ใช่จุดที่ต้องถาม) | เป็นเอกสารหลักที่คำนวณ WHT จริงทุกครั้งที่ `wht_amount>0` |
| `retention_release` | **ไม่ออก** (ไม่ใช่จุดที่ต้องถาม — เป็นผลจากการยืนยันฐาน WHT ในส่วน 2 แล้ว) | WHT ของงวดนั้นถูกคำนวณและหักไปครบแล้วตอน `progress` (ฐาน WHT = มูลค่างวดเต็ม ไม่ลดด้วย retention) การคืน retention ภายหลังจึงเป็นแค่จ่ายเงินสดที่เคยตั้งภาระภาษีไว้แล้ว ไม่ใช่รายได้ใหม่ที่ต้องหัก WHT ซ้ำ |
